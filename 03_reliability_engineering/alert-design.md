# Alert 설계 원칙

## 1. 사용자가 겪는 실패부터 정의한다

GPU 사용률이 높다는 사실보다 접수한 OCR 작업이 약속한 시간 안에 완료되는지가 중요하다. 다음 SLO는 학습용 가정이며 실제 서비스 목표가 아니다.

> 최근 30일 동안 접수된 유효 작업의 99%가 접수 후 30초 안에 성공한다.

입력 크기와 페이지 수에 따라 서비스 등급을 나누고, 유효 작업의 정의와 제외 사유를 명시한다. 끝난 작업만 분모로 잡으면 멈춘 작업이 통계에서 사라진다. 접수 시각 기준 집단을 평가하되 30초의 관찰 시간이 지난 작업을 판정한다. deadline이 지났는데 미완료인 작업도 실패에 포함한다.

## 2. 관측할 지표

| 지표 | 목적 |
|---|---|
| 접수→결과 조회 가능 시간 | 사용자 체감 지연 |
| deadline 초과율·최종 실패율 | SLO 위반 |
| 가장 오래된 대기 작업의 나이 | 장기 적체 감지 |
| Kafka lag·유입률·완료율 | backlog와 처리 능력 비교 |
| GPU 추론 시간·메모리·OOM 수 | 추론 병목 진단 |
| DB 저장 지연·outbox 미발행 나이 | 저장 및 전달 병목 진단 |

평균만 보면 느린 꼬리 구간이 숨는다. p95/p99를 함께 보되 표본 수가 적은 구간은 해석에 주의한다. 완료 샘플의 latency와 미완료 작업 나이를 함께 본다.

## 3. 에러 버짓으로 긴급도를 정한다

`burn rate = 관측 실패 비율 / 허용 실패 비율`이다. SLO 99%에서 실패율 5%는 burn rate 5다. 짧은 창과 긴 창을 함께 평가하면 순간 잡음과 지속 문제를 구분할 수 있다. [Google SRE의 SLO 기반 알람](https://sre.google/workbook/alerting-on-slos/)

실습에서는 빠른 소진을 호출 알람으로, 느린 소진을 조사 티켓으로 구분해 본다. 창 길이와 임계값은 트래픽·대응 시간에 맞춰 결정하며 책의 값을 그대로 운영 기준으로 복사하지 않는다.

## 4. 알람 메시지에 담을 내용

서비스와 환경, 실제 값과 임계값, 지속 시간, 영향을 받는 작업 비율, 대시보드, runbook, 담당자를 포함한다. job_id 같은 고유값은 로그에서 찾는다. 알람 label은 service·stage·error_code처럼 제한된 집합으로 구성한다.

실습: 트래픽 급증과 Worker 정지를 각각 주입해 알람이 실제 사용자 영향과 맞게 발생하는지 확인한다.
