# Recovery 전략

## 1. 프로세스 재시작과 작업 복구는 다르다

Worker가 다시 떠도 DB에 RUNNING으로 남은 작업은 자동 복구되지 않는다. 프로세스 생존, 메시지 재전달, 작업 소유권 회수, 최종 결과 확인을 각각 설계한다.

## 2. 장애별 Runbook

| 증상 | 초기 확인 | 조치 | 성공 기준 |
|---|---|---|---|
| Worker heartbeat 소실 | 노드·프로세스·최근 배포 | 대체 Worker 준비, lease 만료 회수 | 미완료 작업 나이 감소 |
| 반복 GPU OOM | 입력 크기·batch·동시 실행 | 유입 제한, batch 축소, 문제 입력 격리 | OOM 멈춤과 처리량 회복 |
| DB 지연 | 잠금·연결 풀·스토리지 | 쓰기 동시성 제한, 원인 해소 | 저장 지연과 backlog 감소 |
| Kafka 연결 장애 | 브로커·네트워크·인증 | 무한 메모리 적재 중단, 재연결 | 발행·소비 재개 |
| 특정 모델 오류 급증 | 모델 버전별 오류 | 검증된 버전으로 신규 유입 전환 | 오류율 회복 |

이미 접수한 job의 모델 버전은 임의로 바꾸지 않는다. 필요한 모델을 제공할 수 없으면 명시적 실패 또는 별도 재실행 정책을 적용한다.

## 3. Lease 회수

주기적인 스캐너가 만료된 RUNNING 행을 조건부 갱신한다. 재시도 예산이 남았으면 RETRY_WAIT과 next_retry_at, outbox를 한 트랜잭션에 저장한다. 소진했으면 FAILED와 원인을 기록한다. 여러 스캐너가 동시에 실행돼도 한 번만 전이되도록 한다.

복구 Worker는 새로운 attempt를 획득한다. 기존 Worker의 늦은 완료는 token으로 거절한다. 만료 시간 판단에는 DB 기준 시각을 사용하고, 긴 일시 정지와 clock 차이를 고려한다.

## 4. 자동 복구의 제한

재시작 횟수와 시간당 확장 상한, cooldown을 둔다. 같은 실패가 반복되면 자동 조치를 멈추고 호출한다. DB가 병목일 때 Worker를 늘리면 장애가 커질 수 있다. 모델 warmup을 완료한 인스턴스만 준비 상태로 전환한다.

축소·배포 시 새 작업 획득을 중지하고 진행 중 작업을 제한 시간 동안 마무리한다. 종료된 작업은 완료 offset만 커밋하고, 남은 작업은 lease 복구가 처리한다.

## 5. 복구 목표와 훈련

RTO는 복구까지 허용하는 시간, RPO는 허용하는 데이터 손실 범위다. 영속 접수 작업의 논리적 유실을 허용하지 않는 목표라면 DB 백업·복제, Kafka 보존, 입력 보존까지 함께 검증해야 한다. at-least-once 설정만으로 모든 장애의 무손실을 선언할 수 없다.

격리 환경에서 Worker 종료, DB 일시 차단, relay 정지를 주입하고 탐지 시간·처리 재개 시간·backlog 해소 시간을 따로 기록한다.
