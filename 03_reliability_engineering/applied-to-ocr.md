# 신뢰성 엔지니어링 — OCR 적용 사례

## 1. 사용자 증상에서 시작하는 조사

학습 시나리오: 평소 정상인 OCR 작업이 deadline을 넘기고 대기 작업이 쌓인다. 수치와 원인은 실제 장애 보고가 아닌 실험 가정이다.

1. 최근 접수 집단의 deadline 초과율과 미완료 작업 나이를 확인한다.
2. 입력 토픽과 결과 토픽 중 어디에서 적체되는지 나눈다.
3. 다운로드·전처리·GPU·후처리·DB 저장 시간을 비교한다.
4. 최근 배포, 모델 버전, 입력 크기 분포 변화를 확인한다.
5. 병목 단계에만 조치를 적용하고 사용자 지표의 회복을 확인한다.

## 2. 서로 다른 두 장애

**GPU 병목:** 입력 대기가 증가하고 추론 실행 시간이 길다. 큰 이미지 유입이 늘었다면 크기 제한이나 shape bucket을 확인한다. 측정상 batch 효율이 좋아지고 deadline에 여유가 있다면 batch를 조정한다. 추가 GPU는 모델 적재와 warmup 시간까지 고려한다.

**DB 병목:** 추론은 끝나지만 결과 확정이 느리다. Worker 증설을 멈추고 Writer 동시성과 DB 잠금을 확인한다. Async Writer를 쓰는 경우 결과 토픽의 가장 오래된 이벤트 나이를 본다. 입력 토픽 lag만 정상이라고 복구 완료로 판단하지 않는다.

## 3. 장애 훈련 표

| 주입 | 기대하는 보호 | 기록할 결과 |
|---|---|---|
| 추론 중 강제 종료 | lease 만료 후 재획득 | 복구 시간, 중복 추론 횟수 |
| DB 저장 직후 종료 | 결과 멱등성 | 결과 중복·유실 여부 |
| 큰 이미지 반복 유입 | 자원 제한과 격리 | 정상 작업의 deadline 영향 |
| outbox Relay 정지 | 영속 미발행 이벤트 보존 | 알람 시간, 재개 후 해소 시간 |
| 메트릭 수집 중단 | 결측 감지 | 조용한 실패 여부 |

## 4. 장애 기록 양식

발생·탐지·완화·복구 시각, 영향 작업 수, 최초 증상, 원인 증거, 효과가 있었던 조치, 재발 방지 항목과 담당자를 기록한다. 원인 추측은 확인된 사실과 구분한다. 복구 후에도 최종 미완료 작업과 DLQ를 대조해 누락을 확인한다.
