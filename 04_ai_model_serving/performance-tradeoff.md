# Latency vs Throughput Tradeoff

## 1. 측정 경계를 먼저 정한다

```text
T_total = 접수 + 큐 대기 + 다운로드/전처리
          + batch 대기 + GPU 실행 + 후처리 + 결과 영속화
```

순차 단일 작업의 개념적 분해다. 실제 단계가 겹치면 trace의 critical path로 해석한다. GPU 실행 시간만 측정하고 서비스 응답 시간이라고 부르면 큐와 DB 병목을 놓친다.

## 2. 처리량과 대기열

도착률 λ가 지속 가능한 완료율 μ보다 크면 backlog가 계속 증가한다. 안정적인 구간에서 Little의 법칙 `L = λW`로 평균 시스템 내 작업 수와 평균 체류 시간의 관계를 점검할 수 있다. 예를 들어 초당 20개가 완료되고 평균 체류 시간이 2초라면 평균 체류 작업 수는 약 40개다. p95에 그대로 적용하는 공식은 아니다.

현재 backlog가 Q이고 앞으로 일정한 μ > λ가 유지된다는 단순 가정에서 해소 시간은 `Q / (μ - λ)`다. 입력 크기 변화와 warmup이 있으면 오차가 커진다.

## 3. 가상 측정 예시

다음은 해석 연습용으로 만든 수치이며 벤치마크 결과가 아니다.

| 설정 | 완료 처리량 | 전체 p95 | 판단 |
|---|---:|---:|---|
| batch 1 | 20 jobs/s | 180 ms | 지연 기준선 |
| batch 4 | 48 jobs/s | 240 ms | 처리량 증가와 대기 비용 |
| batch 8 | 55 jobs/s | 420 ms | 추가 이득 대비 지연 증가 |

p95 목표가 300ms라면 이 조건에서 batch 8은 부적합하다. 실제 판단에는 입력 분포, 실패율, 비용을 함께 사용한다.

## 4. 벤치마크 절차

1. GPU·모델·정밀도·입력 분포·동시성을 고정한다.
2. cold start와 warm 상태를 분리한다.
3. 도착률을 단계적으로 올리며 steady state와 포화 구간을 확인한다.
4. 완료율, p50/p95/p99, 큐 나이, 오류율, peak memory를 기록한다.
5. 대표 혼합 입력과 burst에서도 같은 목표가 유지되는지 확인한다.

응답을 받은 뒤 다음 요청을 보내는 부하 생성기만 쓰면 느려진 서버에 요청도 줄어 과부하가 가려질 수 있다. 일정 도착률 실험과 클라이언트 동시성 실험을 구분한다. timeout과 거절도 결과에 포함한다.

## 5. 선택 기준

온라인 OCR은 deadline과 꼬리 지연을 먼저 충족하고 그 안에서 처리량을 높인다. 오프라인 대량 작업은 완료 기한과 GPU당 처리 비용을 우선할 수 있다. 같은 모델이라도 두 트래픽의 큐와 자원 예산을 분리할 이유가 있다.
