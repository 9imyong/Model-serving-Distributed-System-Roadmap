# ADR-003: 병목 단계별 Scaling 전략

- 상태: 제안 — 부하 시험으로 임계값 확정 필요
- 범위: Consumer, CPU 전처리, GPU, Writer 확장

## 배경

lag가 증가할 때 Worker를 일괄 증설하면 DB 연결이나 GPU 메모리 경쟁이 악화될 수 있다. 큐 나이와 단계별 처리 시간을 근거로 병목 자원만 확장한다.

## 제안 결정

| 관측 | 우선 검토 |
|---|---|
| GPU가 대기하고 다운로드/전처리가 느림 | CPU 풀·입력 I/O |
| GPU 포화, 추론 큐 나이 증가 | batch 효율·GPU 추가 |
| 결과 저장 지연과 DB 부하 증가 | 쿼리·잠금·Writer 동시성 제한 |
| Consumer 유휴, 파티션 수가 적음 | 파티션 전략과 실행 풀 구조 |

기본형 → batching → Async Writer를 무조건 순서대로 도입하지 않는다. batching은 추론 효율, Async Writer는 저장 경로 분리에 대한 서로 다른 선택이다.

## 용량 추정

GPU 한 장의 실측 처리량이 q이고 목표 도착률이 λ일 때, 목표 사용 비율 u를 두면 초기 추정은 `ceil(λ / (q × u))`다. u는 부하 변동을 흡수하기 위한 여유이며 예를 들어 0.7을 실험할 수 있다. 실제 확장이 선형인지 CPU·DB 병목을 포함한 부하 시험으로 확인한다.

예: 동일한 입력 분포에서 q=20 jobs/s, λ=50 jobs/s, u=0.7이라면 초기 후보는 GPU 4장이다. 측정 결과나 구매 권장값이 아니라 계산 예시다.

## 확장·축소 정책

지속적인 큐 나이 증가와 용량 부족을 함께 보고 확장한다. 최대 replica 수, 비용 상한, warmup 시간, cooldown을 둔다. 낮은 부하가 충분히 지속된 뒤 축소하고, 진행 작업을 drain한다. Kafka 파티션 추가는 key 배치에 영향을 주므로 단순 replica 조정과 별도로 검토한다.

## 검증·재검토

정상 부하, burst, 큰 이미지 혼합, GPU 한 장 손실을 시험한다. deadline 달성률과 작업당 비용이 개선되는지 확인한다. 증설해도 완료율이 증가하지 않으면 추가 확장을 멈추고 다음 병목을 찾는다.
