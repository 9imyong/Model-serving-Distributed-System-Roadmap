# Strong Consistency vs Eventual Consistency

## 1. 무엇을 보장할 것인가?

OCR Worker A가 작업을 완료했는데 Worker B나 조회 API는 여전히 `RUNNING`을 읽을 수 있다. 이때 허용할 수 있는 지연과 절대로 깨지면 안 되는 규칙을 구분해야 한다.

이 문서에서 Strong Consistency는 **선형화 가능성(linearizability)**을 뜻한다. 완료된 쓰기 이후 시작한 읽기는 그 쓰기 또는 더 나중의 쓰기를 관찰한다. 동시에 진행되는 연산에는 실시간 순서와 양립하는 하나의 순서가 있어야 한다. 모든 서버가 물리적으로 같은 순간에 갱신된다는 의미는 아니다.

Eventual Consistency는 추가 갱신이 없고 복제·전달이 계속 진행되면 복제본이 같은 상태로 수렴한다는 보장이다. 이것만으로 수렴 시간의 상한이나 자신의 쓰기를 즉시 읽는 성질까지 보장하지 않는다.

## 2. 비교

| 관점 | Strong | Eventual |
|---|---|---|
| 읽기 | 완료된 최신 쓰기와 실시간 순서 보장 | 오래된 값이 보일 수 있음 |
| 조정 비용 | 합의·동기화가 필요할 수 있음 | 비동기 전달로 경로를 분리할 수 있음 |
| 네트워크 분리 | 보장을 유지하려면 일부 요청 거절·대기 가능 | 가용성을 선택하면 충돌 해결 필요 |
| OCR 적용 | 작업 소유권, 최종 결과 확정 | 검색 색인, 통계, 조회 캐시 |

강한 일관성이 있다고 비즈니스 규칙이 자동으로 지켜지는 것은 아니다. 허용 상태 전이와 트랜잭션 범위를 별도로 정의해야 한다. 반대로 eventual 방식도 재시도·충돌 해결·누락 복구가 없으면 수렴하지 않는다.

## 3. 일관성, 격리 수준, 멱등성은 다른 축이다

- **일관성 모델:** 서로 다른 클라이언트가 쓰기와 읽기를 어떤 순서로 관찰하는가?
- **트랜잭션 격리:** 동시에 실행되는 트랜잭션이 서로 어떤 영향을 주는가?
- **멱등성:** 같은 논리 요청을 반복해도 최종 효과가 동일한가?

Serializable은 트랜잭션을 어떤 직렬 순서로 설명할 수 있다는 뜻이며, 그 자체로 외부 실시간 순서까지 보장한다는 뜻은 아니다. PostgreSQL의 조건부 UPDATE는 경쟁하는 행 갱신을 보호하는 도구이지, 캐시와 모든 읽기 복제본을 포함한 시스템 전체의 선형화 보장은 아니다. [PostgreSQL 격리 수준](https://www.postgresql.org/docs/current/transaction-iso.html)

## 4. OCR에서의 설계

권위 있는 jobs DB에서 `SUCCEEDED`는 결과가 영속화되어 조회 가능하다는 뜻으로 정한다. 성공 상태와 결과 포인터를 하나의 트랜잭션에서 확정하고, 캐시는 이후 갱신한다. 완료 직후 읽기가 중요하면 해당 조회는 primary로 보내거나 버전 기반으로 캐시를 우회한다.

예를 들어 작업 버전 8에서 완료 이벤트를 받았는데 캐시가 버전 7이라면, 버전 7을 최종 결과로 반환하지 않고 원본 DB를 조회한다. 단순 TTL은 지연을 줄일 뿐 최신 읽기를 증명하지 않는다.

## 5. 확인 실습

1. 캐시 갱신을 지연시킨 뒤 완료 직후 조회 결과를 비교한다.
2. 동일 작업을 두 Worker가 동시에 획득하도록 만들고 승자가 하나인지 확인한다.
3. 네트워크 단절 시 요청을 기다리게 할지 실패시킬지 API 계약으로 설명한다.
