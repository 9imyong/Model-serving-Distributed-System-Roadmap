# DLQ & Retry 패턴

## 1. 실패를 분류한다

| 실패 | 예시 | 대응 |
|---|---|---|
| 일시적 의존성 장애 | DB timeout, 저장소 503 | 제한된 재시도 |
| 입력 문제 | 손상 이미지, 지원하지 않는 포맷 | 명시적 실패, 필요하면 DLQ |
| 자원 문제 | 특정 큰 입력에서 OOM | 크기 제한·batch 축소 등 정책 적용 |
| 코드·스키마 문제 | 역직렬화 실패 | 격리하고 수정 후 재처리 |

같은 입력으로 OOM이 반복된다면 단순 재시도는 GPU 부하만 늘린다. 시스템 전체 장애 중에는 빠른 반복 재시도를 줄이고 유입을 제한한다.

## 2. 재시도 예산

설명용 full jitter 규칙은 다음과 같다. attempt는 첫 재시도에서 0이다.

```text
delay = random(0, min(max_delay, base_delay * 2^attempt))
```

횟수 상한과 전체 deadline을 함께 둔다. 예를 들어 최대 5회, 전체 10분은 실험용 정책이며 실제 SLA와 장애 지속 시간에 맞춰 정한다. DB에 `next_retry_at`, `attempt`, `error_code`를 저장해 재시작 후에도 예약이 유지되게 한다.

## 3. 전달 실패를 다시 만들지 않는다

원본 offset을 먼저 커밋하고 retry/DLQ에 보내면 그 사이 종료 시 메시지가 사라진다. Kafka 내부 이동이라면 목적지 발행과 원본 offset을 트랜잭션으로 묶을 수 있다. DB 상태 변경이 포함되면 상태와 outbox를 함께 확정한다. [Kafka 트랜잭션](https://kafka.apache.org/41/design/design/)

Kafka 토픽 자체가 임의의 예약 시각에 메시지를 자동 배달하는 타이머는 아니다. 지연 토픽 단계 또는 DB 스케줄러처럼 대기 구현을 명시해야 한다. Consumer 스레드에서 오래 sleep하면 같은 파티션의 뒤 작업과 poll을 막는다.

## 4. DLQ 운영

DLQ에는 event_id, job_id, 원본 topic/partition/offset, schema_version, 오류 코드, 시도 횟수와 발생 시각을 둔다. OCR 원문 전체 대신 접근 제어된 입력 참조를 사용한다.

DLQ는 자동 해결 장치가 아니다. 담당자·보존 기간·재처리 속도 제한을 정한다. 일시 실패는 동일 job_id로 재시도하고, 이미 최종 FAILED인 작업의 수동 재실행은 새 job과 parent_job_id를 사용한다. 재처리 전에 원인 수정과 스키마 호환성을 확인한다.

## 5. 실습

손상 이미지 한 장이 뒤의 정상 작업을 막지 않는지, retry 전송 중 종료해도 작업이 사라지지 않는지, 재시도 예산 소진 시 최종 상태가 기록되는지 확인한다.
