# Offset Commit 전략

## 1. Commit은 처리 책임을 넘기는 경계다

커밋 offset은 해당 파티션에서 **다음에 읽을 위치**다. offset 42까지 안전하게 처리했다면 43을 커밋한다. 결과 저장 전에 커밋하면 장애 시 재전달 기회를 잃는다. 저장 후 커밋하면 중복은 생길 수 있으므로 멱등 처리가 필요하다. [Kafka Consumer Position과 전달 의미론](https://kafka.apache.org/41/design/design/)

## 2. 동기 저장 경로

```text
poll → 작업 획득 → 추론 → 결과 영속화와 상태 확정 → commit(offset + 1)
```

자동 commit을 비활성화하고 애플리케이션이 완료 경계를 관리한다. commit 실패 시 이미 저장된 결과를 지우지 않는다. 재전달 시 DB 상태를 확인하고 기존 결과를 사용한다.

진행 중인 중복 메시지는 완료된 작업과 다르다. 독립적인 lease 스캐너와 영속적인 재시도 경로가 보장되지 않는다면 무조건 commit해서는 안 된다.

## 3. 병렬 처리의 함정

| offset | 상태 |
|---|---|
| 40 | 완료 |
| 41 | 처리 중 |
| 42 | 완료 |

이 경우 커밋 가능한 위치는 41이다. 43을 커밋하면 재시작 시 미완료 41을 건너뛴다. 파티션별로 완료 집합을 관리하고, 연속해서 완료된 구간의 다음 위치만 커밋한다. 구현이 어렵다면 파티션별 순차 처리부터 시작한다.

## 4. 긴 추론과 Rebalance

poll 간격이 Consumer의 허용 간격을 넘지 않도록 설계한다. 별도 실행기로 추론을 보내더라도 Consumer API의 스레드 안전성 규칙을 지켜야 한다. 내부 큐가 가득 차면 파티션을 pause하고 필요한 poll을 계속하는 구조를 검토한다.

파티션 회수 시 새 작업 접수를 멈추고, 완료한 연속 구간만 커밋한다. 늦게 끝난 이전 Worker의 쓰기는 attempt token으로 차단한다. 설정 시간을 무작정 늘리면 장애 인지가 느려질 수 있다.

## 5. Async Writer 경로

추론 결과를 영속적인 결과 토픽에 넘기면 추론 Consumer의 책임 경계가 달라진다. Kafka transaction으로 결과 이벤트와 입력 offset을 함께 확정하는 방식을 검토한다. Writer는 DB 저장 후 자신의 offset을 커밋한다. 이 시점 전에는 job을 `SUCCEEDED`로 표시하지 않는다.

실습: 41번 작업을 지연시키고 42번을 먼저 완료한 뒤 재시작해 41번이 누락되지 않는지 확인한다.
